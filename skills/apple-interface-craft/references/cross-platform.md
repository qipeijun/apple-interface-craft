# 跨平台转译：理念、组件与实现

本文件是基于 HIG 的工程应用建议，不是 Apple 对非 Apple 平台的规范。先识别用户任务和实际运行时，再选模式；框架名称不能证明底层能力。

## 三层决策

1. **可迁移原则**：清晰层级、熟悉行为、用户控制、及时反馈、保持上下文、可恢复、包容性、内容优先和有意义的动效。
2. **组件与任务决策**：为什么用表格或列表、局部编辑或独立页面；选择与提交是否分离；取消丢弃什么；返回保留什么。使用 [interaction.md](interaction.md) 的契约按需回答。
3. **平台实现**：导航栈、返回键、焦点、语义、尺寸单位、字体缩放、材质、手势、生命周期与权限，服从目标平台、宿主、当前框架及项目契约。

同一个目的可以有不同实现。不要以跨端一致为由覆盖平台惯例；跨端一致首先是对象、状态含义和任务结果一致。

## 运行时分流

| 目标 | 应核实的事实 | 常见误套 |
| --- | --- | --- |
| Apple 原生 | OS 与最低版本、系统组件、对应 HIG 平台章节与 API | 把 iOS 的行为和 Dynamic Type 泛化到 macOS |
| Web | 语义 HTML、路由历史、键盘与焦点、缩放重排、目标浏览器 | 取消按钮焦点、把 pt 当 CSS px、用磨砂证明 Liquid Glass 合规 |
| 小程序 | 宿主版本、渲染模式、已有组件、页面栈、返回、授权和生命周期 | 假定有完整 DOM、Pointer Events、CSS 或浏览器无障碍树 |
| Android / 其他原生 | 系统导航与返回、原生控件、字体及辅助技术设置 | 复制 iOS 手势、导航和字体 API，破坏用户预期 |
| 混合 App / 跨端框架 | 当前页面由谁渲染；导航、键盘、手势和权限由 Web、宿主还是原生桥负责 | 以 CSS 或网页测试推断原生行为已修复 |
| 其他设备 | 观看距离、输入方式、窗口与设备限制、任务持续时间 | 把手机触摸布局机械缩放到遥控、车载或大屏 |

确定目标后才查对应官方文档。宿主能力无法核实时标出缺口；若影响实现，先核实而非补猜测性 API 或兜底分支。

## 从理念落到实际改动

- **高密度管理表格**：清晰不等于改成大卡片。保留比较效率，先检查列层级、批量选择、操作归属、筛选与返回上下文。
- **筛选组件**：即时筛选与“应用”提交是两种契约。后者的临时选择不能在关闭时偷偷写入已生效条件；前者不能伪装成未提交草稿。
- **编辑面板**：关闭、取消、保存、返回可能不同。保留工作不等于自动请求后端；是否存在草稿与恢复机制以项目事实为准。
- **移动端交互**：系统返回、滚动与可访问入口优先；自定义滑动或拖拽必须有任务价值、退出路径与等价操作。

先复用现有设计系统；仅当现有模式妨碍任务时提出局部调整。品牌配色、图标和密度不必 Apple 化；避免以视觉统一为由替换整套组件库。

## 验证边界

按实际改动选择任务路径，例如“进入 → 选择或编辑 → 提交/取消 → 返回”，检查相关状态和上下文。简单按钮不需要完整多端矩阵；共享组件则要检查受影响调用方。

静态方案只能证明设计决策已表达，代码检查只能证明相应实现约束；浏览器验证不证明小程序、WebView 原生桥或真机行为。具体层级见 [implementation-review.md](implementation-review.md)。
